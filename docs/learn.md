## 利用者が決めたこと（2026-11-27）

- 対戦記録1件は、相手の型の割合の計算で上位構築1件分として数える。
- 設定の比べは、GitHub Actions に1つ足して計5つで動かす（選出の表の4つはそのまま）。2026-11-28 に利用者の承認で、比べを6つ・選出の表を12（計18）にし、1日1回から6時間ごとの1日4回に変えた。
- 比べの探索は1手8000回（i5-5300で10秒の実際の回数）。
- 評価関数を学習で作ることは、今回は試さない。

## 対戦記録から数える（P6-1、P6-2）

- 道具：tools/learn/learn-logs.ts。data/logs/ の記録を全部、記録係で最初から当て直し、対戦の終わりの推定を数えて data/priors/learned.json に書く。毎日、裏の計算のまとめで数え直す。
- 当て直しの推定は、上位構築のデータだけの最初の確率で行う。数えた割合を、次の数え方に戻さないためです。
- 数えるもの：
  - 出てきた相手の体ごとの型の確率（合計1）。
  - 相手の6体それぞれが選出に入っていた確率。
  - 相手の6体が上位構築と同じなら、その構築の3体の組の確率。
- 混ぜ方（src/learn/merge.ts、BenchModel）：
  - 型：上位構築に n 回出た種族に記録で L 回出会い、上位構築の型 s の確率の合計が P_s、それ以外の型が G のとき、型 s の重みは w_s → w_s + P_s。それ以外の型の割合は 1/(n+1) → (1+G)/(n+1+L)。それ以外の型の中の持ち物・能力ポイントは、もとの割合を1件分として記録の確率を足す。
  - 選出：種族の「選出に入る割合」と、上位構築ごとの3体の組の割合に、記録の確率を1件分として足す。
- 対戦中の推定（記録係）と、選出の画面の「表のない相手の型」が、混ぜた後の確率を使う。
- 記事の選出の分布に、どの組も同じ割合の分布を1割混ぜた（段階3で作った部分の変更）。記事にない3体の組の確率が0だと、見えた体に合う組がなくなり、記録からも数えられないためです。1割は私が決めた値で、推定です。

## 探索の設定の比べ（P6-3）

- 道具：tools/learn/compare.ts（手伝いは tools/learn/compare-worker.ts、1試合は src/learn/duel.ts）。
- 今の設定は data/learn/settings.json、候補の並びは data/learn/queue.json、比べの途中と結果は data/learn/comparisons/<候補>.json、決まったものは data/learn/history.json。
- 1組＝2試合。構築 X・Y と選出（3体と先発）を決め、「今の設定が X で p1、候補が Y で p2」と「候補が X で p1、今の設定が Y で p2」を、同じ乱数の種で打つ。構築・選出は組の番号から決まった乱数で選ぶ（上位構築199件から無作為。選出も無作為）。
- 両者とも、自分の画面に見えることだけを記録係に入れて相手の型を推定し、仮の盤面を作って、1手8000回探索する（サイトと同じ流れ）。推定の最初の確率は上位構築のデータだけ（記録の割合は混ぜない。比べを毎回同じ条件にするため）。
- 採用の判定（src/learn/decide.ts）：2000試合以上、候補の勝率0.52以上、かつ「勝率 − 誤差の2倍」が0.5を超えたときだけ採用。誤差は「試合を別々と見た標準誤差」と「組ごとの平均から出した標準誤差」の大きいほう。採用したら settings.json を変え、サイトの探索がそれを使う。
- 最初の候補：広げ方の定数0.5、先読み6ターン、仮の盤面12。
- 時間で区切り、次の回は保存した組から続ける（途中の組の残りの半分も）。

### 1つの手伝いで同じ処理に2つの Showdown

本当の対戦と記録係には、記録を作る Showdown が要ります。探索には、記録を作らない速さの層を当てた Showdown を使います。速さの層は Showdown 全体に当たるので、同じ処理の中で両方を使うと、本当の対戦の記録も消えます（実際に、メガシンカが記録係に伝わらない不具合が出た）。そこで、Showdown を2つ別々に読み込み（tools/showdown/load.ts の loadShowdownCopy）、片方にだけ速さの層を当てた。

## 見つけて直したずれ

- 相手の特性の表示を拾う部分が、トレースで写した行（`|-ability|主語|写した特性|[from] ability: Trace|[of] 写したもと`）を「写したもとの特性はトレース」と読んでいた。試合の模擬（sim-check）にも同じ誤りがあった。記録の行の読み方を直し、両方で同じ部分（src/learn/viewer.ts の revealFoe）を使う。
- 記録係の最初のターンの前（相手の先発が出たとき）の特性の手がかりに、「その種族が持てない特性は使わない」確かめがなかった。足した。
- 最初のターンの前に「今の状態」で直したものが、ターンを記録した後にページを開き直すと消えていた。当て直しで使うようにした。

## 弱点・残っていること

- 6つに分けて並べる（2026-11-28）：組の番号は 0〜999。分担 k は番号を6で割った余りが k の組だけを打ち、自分の途中のファイル（comparisons/<候補>.shard<k>.json）にだけ書く。6つが終わった後に、まとめの作業（compare.ts --merge）が分担のファイルを comparisons/<候補>.json に足して消し、2000試合に届いたら判定する。前の形（組の番号なし）の記録は、配った順の番号に直して引き継ぐ（138試合・勝率0.540がそのまま残ることを確かめた）。確かめ用の小さい設定で、2つの分担を同時に動かすと組の番号が重ならずに分かれ、途中の組（片方だけ打った組）は次の回に残りの片方だけを打つことを確かめた。
- Actions での確かめ（2026-11-28 12:37 世界標準時、手で15分）：選出の表の12と比べの6の、18の作業が12:37〜12:38に同時に始まり、全部成功。まとめの作業（compare-finish）が分担のファイル6つを足して消し、比べは138試合 → 182試合（組のそろった91組＋途中3組）になって main に保存された。
- 6つ・1日4回にした後の見込み：1試合を平均約540秒（Actions の138試合の平均）とすると、1回280分×4コア×6つで約750試合、1日4回で約3000試合。1回の比べ（2000試合）は1日以内の見込み。確認していません。
- **（6つ・1日4回にする前）1回の比べ（2000試合）には、約2週間かかる見込みでした。** Actions で測った1試合は275〜493秒（7試合、2026-11-27）で、決着がつかず60ターンまで続いた試合は1703秒でした。平均を約420秒とすると、2000試合で4コア約58時間、毎日300分ずつで約12日です。利用者に伝えた見積もり「約5日」より長いです。
- 比べの試合は、上位構築から無作為の構築・無作為の選出で打ちます。利用者のパーティを使った試合ではありません。倒れた後の交代先は、両者とも盤面の並びの若い番号です。
- 記録係が追っていない状態（技の固定、かなしばり、アンコール等）のために、探索のいちばんの手が本当には選べないことがあります。そのときは、選べる手のうち探索の回数がいちばん多い手を打ちます（12試合で22回）。両方の側に同じように起きます。
- 「それ以外の型」の技の候補は、記録から学びません（技の割合は上位構築の型の分だけが動く）。
- シーズンが変わったときに古い記録の重みを下げる仕組みは、まだありません（指示文の「後から足す指示」で行う）。
- 指示文 4-5. の「上位構築どうしを AI で対戦させ、型の相性を増やす」は、利用者のパーティ対上位構築の表（段階5）までで、上位構築どうしの対戦はしていません。
