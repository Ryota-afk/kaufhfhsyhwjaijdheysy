# 対戦エンジンの作りと、Showdown をそのまま使うかの判断

最終更新：2026-11-27

## 結論（2026-11-27 確定）

指示文 4-1. の手順に従い、「ブラウザの中の計算が、6. の速さの目標（i5-5300 のPC相当で、1ターンの計算が10秒以内）に足りるか」で判断しました。i5-5300 の実機での測定でも下の基準を満たしたので、**Showdown 本体（＋速さの層）を使います**。基準は利用者が承認しました（2026-11-27）。

余裕は約2倍しかありません。実機では、10秒で約7800〜9200回に対して、基準は4000回です。段階4で評価の計算を足して探索1回が重くなったときに、また測ります。基準を下回るなら、次の順で手を打ちます。

1. 速さの層を深くする
2. 相手の型の仮定の数を減らす
3. 専用エンジンを作る

探索の回数を増やしたときに強さがどれだけ上がるかも、まだ分かっていません。段階4で確かめます（下の「段階4で確かめること」）。

## 判断の基準

指示文の出力の要件は、「上位3手と勝率。勝率の差が誤差より小さいときは、そうと分かる表示にする」です。そこで、「足りる」の基準を次のように決めました。

| 項目 | 値 | 理由 |
|---|---|---|
| 候補手1つあたりの探索の回数 | 400回以上 | 勝率50%付近の誤差（標準誤差）が √(0.5×0.5÷400) = 0.025、つまり ±2.5ポイントになる。勝率を「62%」のように表示して意味のある細かさ |
| 根元の候補手の数 | 最大10 | 技4つ＋メガシンカつきの技4つ＋交代2つ |
| 必要な探索の回数（相手の型の仮定8通りの合計） | 4000回以上（10秒で） | 10候補×400回。どの候補にも同じだけ回ったときの最低限 |
| 1秒あたりに必要な回数 | 400回以上 | 4000回÷10秒 |

「探索1回」は、盤面の複製＋2ターン打つ処理で測りました。実際の探索で使う評価の計算は、まだ含まれていません。

| 参考：Node.js 22 での1秒あたりのターン数 | 約1300 | 約2900 |

### 前回の推定との違い

前回は、この計算機の測定を公開の性能値で換算して、「Worker 2つで1秒あたり約1250〜1700回」と推定しました。実測は779回で、推定より大幅に少なかった理由は2つです。

- 1つの Worker の速さが、この計算機の約2.9分の1でした（562回÷1600回）。仮定した「1.8〜2.4倍遅い」の範囲を超えていました。
- Worker を増やしたときの伸びが小さく、2つで1.4倍、4つで1.6倍でした。ノートPCの2コアCPUは、たくさん並べると1コアあたりの周波数が下がるためと考えられます（確認していません）。

## 段階4で確かめること

1. 探索の回数と強さの関係を測る。例：4000回と16000回のAIどうしで対戦させ、指示文 4-5. の基準（2000試合以上、勝率0.52以上、かつ誤差の2倍を引いても0.5超）で差があるかを見る。差があれば、回数を増やす価値がある。その場合、専用エンジン（Showdown と照合しながら作る）を検討し直す。
2. 評価の計算を足した後の、探索1回の時間（実機で測り、10秒で4000回を満たすか）。

## 参考：速い専用エンジンとの差

Foul Play が使うエンジン（poke-engine、Rust）の説明書には、「100ミリ秒の探索で25000回」という実行例が載っています（[poke-engine の README](https://docs.rs/crate/poke-engine/0.0.28/source/README.md)、計算機は書かれていない）。単純に比べると、こちらの実機での1Workerの562回/秒は、その約450分の1です（計算機が違うので目安）。数だけで見れば、専用エンジンは大幅に多く探索できます。今回の判断は「指示文の速さの目標に足りるか」によるもので、「専用エンジンより速い」という意味ではありません。

## 速さの層（src/engine/fast.ts、src/engine/clone.ts）

乱数の使い方を変えないので、同じ乱数の種なら結果は Showdown と完全に一致します（照合で確かめている）。

| 部分 | 内容 |
|---|---|
| 記録を作らない | 対戦の記録の文字列（`add` など）を作らない |
| 処理先の一覧 | イベントごとに、その処理を持つ効果の一覧を最初に作り、持たない効果は調べずに飛ばす。処理先を集める順番は Showdown と同じ |
| 技データの写し方 | 技を使うたびの写し（`getActiveMove`）を、まとめて浅く写してから中の入れ物だけ深く写す形にする。技の効果の定義（condition）は共有する |
| 速い複製 | 図鑑のデータ（Showdown 側で書き換え禁止）は共有し、対戦の状態だけを、参照のつながりを保って写す。図鑑のデータかどうかは、クラスの実物で見分ける（サイトの組み立てで名前が変わるため） |

## ブラウザで動かす形（tools/browser/build-showdown.ts）

Showdown の組み立て済みのファイル（vendor/showdown/dist）を、esbuild で1つの ESM ファイル（.build/showdown-browser.mjs、約3.4MB、サイトに入れると縮めて約2MB）にまとめます。Node だけの機能は次のとおり差し替えます。

- ファイルの場所：仮の場所の文字列にする。
- 実行時に決まるデータの読み込み：組み立て時に入れたデータを引く。
- mod の一覧・`path`・`node:crypto`・`node:util`：ブラウザ用の置き換えにする。

覚えられる技の表（Learnsets）は対戦の処理に使わないので空にしました。結果が変わらないことは、上の一致の確かめ（1000 / 1000）で見ています。

## これまでの経緯

- 2026-11-26：Showdown をそのまま使うことに決めた。しかし、指示文の手順（ブラウザで、i5-5300 相当で、速さの目標に足りるか）の測定をせずに決めていた。また「作り直しても大きく速くならない」と書いたが、確かめたのは「Showdown の汎用のイベントの仕組みを移植しても速くならない」ことだけだった。処理の順番を直接書き込む専用エンジンなら速くなりうるので、この書き方は誤りだった。
- 2026-11-27：利用者の指摘を受け、手順どおりにブラウザでの測定と基準を作り直した。実機で測り、基準を満たしたので Showdown を使うことに確定した（この文書）。

## 弱点・残っていること

- エンジンは Showdown の誤りもそのまま引き継ぎます。Showdown と実機がずれている場合は、ここでは見つけられません。
- 裏の計算（GitHub Actions）で2000試合の比較をするのに必要な時間を見積もりました。1手4000回の探索、1試合20ターンとすると、1試合で約16万回です。この計算機（クラウド）のWorker 4つの速さ（1秒あたり約4700回）なら1試合約34秒、2000試合で約19時間かかります。6時間の区切りで4回ほどに分けることになります。GitHub の実行機の速さは確認していません。
- 照合の盤面は、場に出ている1匹の一時的な状態として8種類だけを置いています（みがわり、こんらん、やどりぎのタネ、ちょうはつ、こだわりの固定、あくび、きあいだめ、のろい）。それ以外は、打っている間に生じたものだけを照合しています。
