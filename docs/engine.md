# 対戦エンジンの作り

最終更新：2026-11-26（段階1）

## 結論

対戦エンジンは、Pokémon Showdown 本体（コミット `c7fa6f16503de510c319239b5b2d29d4f7abd8c4`、形式 `gen9championsbssregmc`）をそのまま使います。その上に、探索のための「速さの層」を足しました。専用のエンジンを一から作ることはしていません。

## そう決めた理由

1. Showdown の1ターンの時間の大半は、イベントの処理先を探す部分（`getCallback`、`findEventHandlers`）でした。この仕組みは、特性・持ち物・技の処理を Showdown と同じ順番で呼ぶためのものです。処理の順番を Showdown に合わせたまま作り直すと、同じ仕組みが必要になります。そのため、作り直しても大きくは速くなりません。
2. 指示文 4-1. に挙がった過去のずれ（まきびし、連続技の急所、吸い取る技の順番など）は、独自実装で生まれたものです。Showdown の処理をそのまま使えば、こうしたずれは仕組みのうえで起きません。
3. 速さの層は、乱数の使い方を変えません。そのため照合では「同じ乱数の種で結果が完全に一致するか」という、割合の比較より厳しい確かめができます。

## 速さの層（src/engine/fast.ts、src/engine/clone.ts）

| 部分 | 内容 |
|---|---|
| 記録を作らない | 対戦の記録の文字列（`add` など）を作らない |
| 処理先の一覧 | イベントごとに、その処理を持つ効果（状態・特性・持ち物・場の状態など）の一覧を最初に作る。持たない効果は調べずに飛ばす。処理先を集める順番は Showdown と同じ |
| 技データの写し方 | 技を使うたびの写し（`getActiveMove`）を、まとめて浅く写してから中の入れ物だけ深く写す形にする。技の効果の定義（condition）は書き換えられないので共有する |
| 速い複製 | 図鑑のデータ（Showdown 側で書き換え禁止になっている）は共有し、対戦の状態だけを、参照のつながりを保って写す |

## 速さ（この作業用の計算機：Intel Xeon 2.10GHz の1コア、Node.js 22）

| 測ったもの | Showdown そのまま | エンジン |
|---|---|---|
| 1秒あたりのターン数（ランダムな行動の対戦。準備の時間を除く） | 約1080 | 約2700〜3000 |
| 盤面の複製1回（対戦の途中の盤面、十分に繰り返した後） | 約570〜710µs（付属の serialize→deserialize） | 約130〜160µs |

測り方：`npm run bench -- plain 10`、`npm run bench -- fast 10`、`npx tsx tools/dev/clone-count.ts`。

i5-5300 のPCでの速さは**確認していません**。段階4で、ブラウザで動く形にしてから測ります。

## 正しさの確かめ

- ランダムな盤面での照合：docs/engine-compare.md（`npm run compare`）
- 指示文 4-1. の項目：docs/rules-check.md（`npm run rules`）
- GitHub Actions の「照合」で、エンジンに関わる変更のたびに 300盤面×20種×4ターンと 4-1. の項目を回す。ずれが1回でもあれば失敗にする。

## 弱点・残っていること

- 速さは Showdown の約2.7倍にとどまります。段階4（10秒で上位3手）と段階6（AIどうしで2000試合以上の比較）で足りるかは、まだ確かめていません。足りなければ、この照合の仕組みで確かめながら、速さの層を深くします（例：ターンの終わりの処理、行動の受け付け、要求データ作りの省略）。
- エンジンは Showdown の誤りもそのまま引き継ぎます。Showdown と実機がずれている場合は、ここでは見つけられません。
- ブラウザで動かす形（Showdown のデータの読み込みを、ブラウザ用に組み直すこと）は、まだ作っていません（段階4）。
- 照合の盤面は、場に出ている1体の一時的な状態として8種類だけを置いています（みがわり、こんらん、やどりぎのタネ、ちょうはつ、こだわりの固定、あくび、きあいだめ、のろい）。そのほかの状態は、打っている間に自然に生じるものだけを照合しています。
